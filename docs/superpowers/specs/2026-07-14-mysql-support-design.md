# MySQL Support Design

## Goal

Add MySQL as a first-class SQL dialect alongside PostgreSQL while preserving ViewDB's source-aware editing, relationship visualization, safe-save guarantees, and existing PostgreSQL behavior.

This phase targets common schema DDL. It does not attempt to model full MySQL dumps, stored procedures, triggers, views, `DELIMITER` blocks, data inserts, or session directives.

## User Experience

- When a SQL file opens, ViewDB automatically detects PostgreSQL or MySQL.
- The toolbar displays the active dialect and offers a selector so the user can correct detection.
- The selected dialect remains attached to the document while it is edited and saved.
- MySQL tables, columns, primary keys, foreign keys, common indexes, `AUTO_INCREMENT`, backtick identifiers, and trailing table options such as `ENGINE=InnoDB` load without losing their original source text.
- SQL generated by visual edits uses PostgreSQL double-quoted identifiers or MySQL backtick-quoted identifiers as appropriate.
- Save validates against the active dialect and retains the existing external-change check, backup, and atomic replacement behavior.

## Architecture

### Dialect model

Introduce a shared `SqlDialect` value with two valid values: `postgresql` and `mysql`. `OpenedDocument` and `FileIdentity` carry this value from native open through parsing, editing, preview, and save.

The frontend parser accepts the dialect explicitly. The parser must not infer dialect internally because parsing and generation need one stable interpretation throughout an editing session.

### Native detection and validation

Keep `pg_query` as the PostgreSQL validator. Add a MySQL-capable Rust SQL parser for schema validation.

Opening a file uses these steps:

1. Inspect strong MySQL syntax markers, including backtick identifiers, `AUTO_INCREMENT`, `UNSIGNED`, and `ENGINE=`.
2. Validate with both dialects where practical.
3. Prefer MySQL when strong MySQL markers are present and MySQL validation succeeds.
4. Otherwise prefer PostgreSQL when PostgreSQL validation succeeds.
5. Fall back to MySQL when only MySQL validation succeeds.
6. Return a combined error when neither dialect accepts the schema.

The bundled example remains PostgreSQL. Saving receives the selected dialect and validates only with that dialect before writing.

### Source-preserving frontend parser

Extend tokenization to recognize backtick-quoted identifiers, including escaped double backticks. Identifier unquoting becomes dialect-aware while still accepting the source form used in the file.

The existing source-range model remains the authority for edits. MySQL-specific clauses that ViewDB does not edit are left untouched in the source. The parser visually models:

- `CREATE TABLE` and `CREATE TABLE IF NOT EXISTS`
- qualified table names
- common MySQL column type expressions, including size and precision parameters
- column and table primary keys
- inline and table-level foreign keys
- nullable and unique constraints
- default expressions
- `AUTO_INCREMENT` as preserved column syntax
- common table-level `KEY`, `INDEX`, and `UNIQUE KEY` definitions without treating them as columns
- trailing table options, including `ENGINE`, charset, and collation, through statement-range preservation

Composite indexes are recognized and preserved but do not require a new visual index editor in this phase. Composite foreign keys are preserved and reported as unsupported when they cannot be represented by the current single-column relationship model.

### SQL generation

All identifier-writing paths receive the active dialect. PostgreSQL uses the existing lowercase-safe unquoted rule and double quotes when quoting is required. MySQL uses the same safe unquoted rule and backticks when quoting is required, escaping embedded backticks by doubling them.

New tables, columns, renames, and relationship patches use the document dialect. Existing untouched syntax remains byte-for-byte preserved through the current patching model.

### Dialect correction

Changing the toolbar dialect reparses the current generated SQL under the selected dialect. The change succeeds only when the frontend can find supported tables. The history is reset because source ranges and dialect-specific quoting semantics have been re-established; the user receives a clear status message. Saving then uses the corrected dialect.

## Error Handling

- Open failures identify that neither PostgreSQL nor MySQL validation accepted the file and include concise errors from both validators.
- Save failures name the selected dialect that rejected the SQL.
- Unsupported but preservable MySQL statements produce warnings rather than preventing the supported schema from opening.
- The app must never silently switch dialect during save.
- Correcting the dialect must not overwrite the source file; it only changes the in-memory interpretation until the user explicitly saves.

## Testing

### Frontend

- Parse a representative two-table MySQL schema with backticks, `BIGINT UNSIGNED AUTO_INCREMENT`, table-level keys, an InnoDB engine option, and a foreign key.
- Resolve MySQL inline and table-level relationships.
- Confirm index definitions are not rendered as columns.
- Confirm MySQL and PostgreSQL identifier quoting and escaping.
- Confirm generated additions and renames use the active dialect.
- Retain all existing PostgreSQL parser and operation tests.

### Native

- PostgreSQL example validation continues to pass.
- Representative MySQL schema validation passes.
- Detection selects MySQL for strong MySQL syntax and PostgreSQL for the bundled example.
- Ambiguous ANSI-compatible DDL defaults to PostgreSQL.
- Saving validates with the supplied dialect and preserves backup/conflict behavior.

### Product verification

- Open a MySQL schema in the native app and confirm the dialect badge, two tables, and relationship.
- Rename a MySQL identifier that requires quoting and confirm backticks in SQL preview.
- Save and reopen the schema without losing engine options or indexes.
- Switch a compatible file's dialect and confirm reparsing and save validation use the corrected selection.

## Compatibility and Scope

PostgreSQL remains the default for the bundled example and ambiguous portable DDL. Existing PostgreSQL files, metadata sidecars, layouts, and safe-save behavior remain compatible.

This phase does not add a complete MySQL dump importer or a visual index editor. Those are separate follow-up projects because they require additional source models and UI workflows.
